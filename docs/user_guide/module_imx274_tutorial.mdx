## Overview

Follow this tutorial to build a player for an IMX274 camera and see how a
`hololink_module` application discovers, configures, and streams from a Holoscan Sensor
Bridge board. Applications using the new `hololink_module` can talk to different HSB
devices transparently, unlike those applications using the legacy API.

An application accesses the capabilities it needs as *services* instead of constructing
device classes directly. A service is requested by type through `get_service`, usually
keyed by the enumeration metadata that identifies a specific board:

<Tabs>

<Tab title="Python" language="python">

```python
  hololink = hololink_module.HololinkInterfaceV1.get_service(metadata)
```

</Tab>
<Tab title="C++" language="cpp">

```cpp
  auto hololink = hololink::module::HololinkInterfaceV1::get_service(metadata);
```

</Tab>
</Tabs>

This indirection is what lets one application drive different boards — and different
revisions of the same board — without recompiling. The [Background](#background) section
explains how; the rest of this page builds a working player first.

## IMX274 player tutorial

This tutorial builds a player that receives video from an IMX274 camera and displays it.
The complete program ships as `imx274_module_tutorial.py` (Python) and
`imx274_module_tutorial` (C++, built from `examples/imx274_module_tutorial.cpp`); the
snippets in each tab are taken from the program in that language. Pick your language
with the tabs. Both programs use the Holoscan SDK 5 API.

### Configuration

You need a Holoscan Sensor Bridge board with an IMX274 camera attached, reachable at its
default address `192.168.0.2`. The IMX274 is a stereo camera pair; at `192.168.0.2` this
tutorial drives the first camera on the device. This tutorial assumes you have built and
are running the demo container as described in [Host Setup](setup.mdx) and
[Build](build.mdx). The program hard-codes its settings, so there is nothing to pass on
the command line.

### Application pipeline

The player is a Holoscan pipeline of five operators. Data flows left to right:

```none
receiver -> csi_to_bayer -> image_processor -> demosaic -> holoviz
```

The first two links each carry two streams: the frame (`tensor`) and its capture
metadata (`metadata`). Only the image goes on to the demosaic, so the metadata output of
`image_processor` stays unconnected; hololink operators skip an unconnected metadata
output.

While data flow starts with the receiver operator, we can't construct it without knowing
some configuration (specifically the receiver buffer size) that comes from the CSI to
Bayer converter. So configure the converter against the camera, read back the frame
size, and build `CsiToBayerOp`:

<Tabs>

<Tab title="Python" language="python">

```python
  converter = hololink_module.CsiToBayerConverter()
  # Configuring the converter tells us how big each received frame is.
  camera.configure_converter(converter)
  frame_size = converter.get_csi_length()
  geometry = converter.geometry()
  csi = graph.op(
      hololink_module.operators.CsiToBayerOp,
      "csi_to_bayer",
      cuda_device_ordinal=cu_device_ordinal,
      geometry=geometry,
      bayer_format=bayer_name,
  )
```

</Tab>
<Tab title="C++" language="cpp">

```cpp
  hololink::module::csi::CsiGeometry geometry;
  // Configuring the converter tells us how big each received frame is.
  camera->configure_converter(
      hololink::module::operators::CsiToBayerOp::make_geometry_adapter(geometry));
  const size_t frame_size = geometry.start_byte
      + geometry.bytes_per_line * geometry.pixel_height + geometry.trailing_bytes;
  // ...
  auto csi = graph.op<hololink::module::operators::CsiToBayerOp>("csi_to_bayer");
  csi.set_params(hololink::module::operators::CsiToBayerParams {
      .cuda_device_ordinal = cu_device_ordinal,
      .geometry = geometry,
      .bayer_format = bayer_format,
  });
```

</Tab>
</Tabs>

`graph.op()` adds an operator to the Holoscan `Graph`. In C++, `set_params()` then
configures it; in Python, `graph.op()` takes the parameters as keyword arguments.
`graph.op()` defers constructing the operator, so the camera reports its geometry
instead of configuring a live operator: into a `CsiGeometry` through an adapter in C++,
and into a `CsiToBayerConverter` in Python.

`RoceReceiverOp` configures itself from the enumeration metadata to listen for data on
the enumerated channel. The `device_start` / `device_stop` callbacks start and stop the
camera around streaming:

<Tabs>

<Tab title="Python" language="python">

```python
  receiver = graph.op(
      hololink_module.operators.RoceReceiverOp,
      "receiver",
      metadata=metadata,
      frame_context=int(cu_context),
      frame_size=frame_size,
      device_start=camera.start,
      device_stop=camera.stop,
  )
```

</Tab>
<Tab title="C++" language="cpp">

```cpp
  auto receiver = graph.op<hololink::module::operators::RoceReceiverOp>(
      "receiver",
      metadata,
      [camera] { camera->start(); },
      [camera] { camera->stop(); });
  receiver.set_params(hololink::module::operators::RoceReceiverParams {
      .frame_context = cu_context,
      .frame_size = frame_size,
  });
```

</Tab>
</Tabs>

Three operators finish the pipeline:

- `ImageProcessorOp` is a `hololink_module` operator that provides a naive ISP of Bayer
  data (e.g. RGGB) using the GPU.
- `BayerDemosaicOp` is a standard Holoscan operator that interpolates the 16-bit Bayer
  grid into 16-bit RGBA.
- `HolovizOp` is a standard Holoscan operator that displays the result.

`BayerDemosaicOp` and `HolovizOp` come from the SDK's vision and visualization modules
(`holoscan::vision` and `holoscan::visualization` in C++, `holoscan_vision` and
`holoscan_visualization` in Python). Both programs open a 1920x1080 window titled
"Holoviz", with one image layer for the camera's 16-bit RGBA frames. The C++ program
adds `HolovizOp` with `hx::add_holoviz()`, one of the helpers it shares with the other
example players (`examples/player_support.hpp`), with the default layer trigger, which
renders each frame as it arrives:

```cpp
  holoscan::visualization::LayerStack layers;
  layers.add_image_layer("video", hx::rgba16_layer(camera->width(), camera->height()));

  // A 1920x1080 window titled "Holoviz" that renders each frame as it arrives.
  holoscan::CompileOptions compile_options;
  auto viz = hx::add_holoviz(graph, "holoviz", std::move(layers), hx::DisplayConfig {}, compile_options,
      cu_device_ordinal);
```

The Python program adds it by its catalog name and draws 60 times a second, as the other
Python players do:

```python
  visualizer = graph.op(
      "holoscan.visualization.HolovizOp",
      "holoviz",
      layers=[
          {
              "port_name": "video",
              "kind": "image",
              "format": "rgba16_unorm",
              "max_width": camera._width,
              "max_height": camera._height,
          }
      ],
      sink={
          "kind": "window",
          # The demosaiced data is linear sensor output: encode to sRGB on write.
          "framebuffer_srgb": True,
          "title": "Holoviz",
          "width": 1920,
          "height": 1080,
          "close_on_escape": True,
      },
      trigger={"kind": "clock", "period_ns": round(1e9 / 60.0)},
  )
```

Wire the operators together:

<Tabs>

<Tab title="Python" language="python">

```python
  graph.add_flow(receiver.tensor, csi.in_tensor, queue_depth=2)
  graph.add_flow(receiver.metadata, csi.in_metadata, queue_depth=2)
  graph.add_flow(csi.tensor, image_processor.in_tensor, queue_depth=2)
  graph.add_flow(csi.metadata, image_processor.in_metadata, queue_depth=2)
  graph.add_flow(image_processor.tensor, demosaic.input, queue_depth=2)
  graph.add_flow(
      demosaic.output,
      visualizer.video,
      queue_policy=hs.QueuePolicy.DROP_OLDEST,
      queue_depth=1,
  )
```

</Tab>
<Tab title="C++" language="cpp">

```cpp
  graph.add_flow(receiver->tensor, csi->input_tensor, hx::pipeline_edge());
  graph.add_flow(receiver->metadata, csi->input_metadata, hx::pipeline_edge());
  graph.add_flow(csi->output_tensor, ip->input_tensor, hx::pipeline_edge());
  graph.add_flow(csi->output_metadata, ip->input_metadata, hx::pipeline_edge());
  graph.add_flow(ip->output_tensor, demosaic->input, hx::pipeline_edge());
  graph.add_flow(demosaic->output, viz->image_layer_input(0), hx::display_edge());
```

</Tab>
</Tabs>

Each link of the chain gets a two-frame queue (`hx::pipeline_edge()` in C++): one frame
being processed and one waiting. The link into `HolovizOp` gets a one-frame queue that
drops the oldest frame (`hx::display_edge()` in C++), so that where `HolovizOp` runs on
a thread of its own, a display that falls behind skips to the newest frame instead of
holding the pipeline back.

### Application initialization

The main program is responsible for finding the board, configuring it, and then running
the pipeline described above.

Get the adapter — the object through which an application discovers and reaches boards —
and wait for the board to announce itself. `wait_for_channel` blocks until the board at
the given IP appears and returns its enumeration metadata:

<Tabs>

<Tab title="Python" language="python">

```python
  adapter = hololink_module.Adapter.get_adapter()
  metadata = adapter.wait_for_channel(HOLOLINK_IP, DISCOVERY_TIMEOUT)
```

</Tab>
<Tab title="C++" language="cpp">

```cpp
  auto& adapter = hololink::module::Adapter::get_adapter();
  hololink::module::EnumerationMetadata metadata
      = adapter.wait_for_channel(HOLOLINK_IP, DISCOVERY_TIMEOUT);
```

</Tab>
</Tabs>

Construct the camera driver from that metadata. **The sensor driver is not a service: it
is linked directly into your application, which is tightly coupled to this sensor.** The
driver resolves the services it needs from the metadata internally:

<Tabs>

<Tab title="Python" language="python">

```python
  camera = hololink_module.sensors.imx274.Imx274Cam(metadata)
```

</Tab>
<Tab title="C++" language="cpp">

```cpp
  auto camera = std::make_shared<hololink::module::sensors::imx274::Imx274Cam>(metadata);
```

</Tab>
</Tabs>

Bring up the board. Fetch the control-plane service, `start()` it to open a socket to
the board, and `reset()` it into a known state. The framework never changes device state
on its own, so you must `reset()` to be sure the board is in a known configuration. Then
configure the camera:

<Tabs>

<Tab title="Python" language="python">

```python
  hololink = hololink_module.HololinkInterfaceV1.get_service(metadata)
  # start() opens the control-plane socket; without it, no device I/O works.
  hololink.start()
  hololink.reset()
  # configure() writes device registers, so it must run after reset().
  camera.configure(CAMERA_MODE)
  camera.set_digital_gain_reg(0x4)
```

</Tab>
<Tab title="C++" language="cpp">

```cpp
  auto hololink = hololink::module::HololinkInterfaceV1::get_service(metadata);
  // start() opens the control-plane socket; without it, no device I/O works.
  if (hololink->start() != HOLOLINK_MODULE_OK) {
      throw std::runtime_error("HololinkInterface::start failed");
  }
  if (hololink->reset() != HOLOLINK_MODULE_OK) {
      throw std::runtime_error("HololinkInterface::reset failed");
  }
  // configure() writes device registers, so it must run after reset().
  camera->configure(CAMERA_MODE);
  camera->set_digital_gain_reg(4);
```

</Tab>
</Tabs>

Run the application. When it exits, `stop()` the control plane to stop streaming and
close the socket:

<Tabs>

<Tab title="Python" language="python">

```python
  graph, options = build_graph(cu_context, cu_device_ordinal, metadata, camera)
  plan = hs.compile(graph, options)
  # ...
  # Run until the window closes or Ctrl+C, then report how the run ended.
  with hs.run_async(plan) as session:
      try:
          session.wait()
      except KeyboardInterrupt:
          # Leaving the block stops the session cooperatively, which stops the camera.
          pass
  # ...
  # Stop streaming data and close up sockets.
  hololink.stop()
```

</Tab>
<Tab title="C++" language="cpp">

```cpp
  const auto plan = holoscan::compile(graph, std::move(compile_options));
  // ...
  // Run until the window closes or Ctrl+C, then report how the run ended.
  auto session = holoscan::run_async(plan, signals);
  session.wait();
  const bool failed = hx::report_session(session, plan);

  // Stop streaming data and close up sockets.
  hololink->stop();
```

</Tab>
</Tabs>

`compile()` turns the graph into an execution plan, after the program has bound the
operators' tensor outputs to the GPU with `bind_tensor_output_device()`. In Python,
Ctrl+C or SIGTERM raises `KeyboardInterrupt` in `session.wait()`, and leaving the `with`
block stops the session cooperatively. `main()` runs everything inside
`hx::run_with_managed_signals()`, and the session runs bound to those managed shutdown
signals: Ctrl+C, like closing the window, stops it cooperatively, so the camera and the
board are still stopped on the way out. `hx::report_session()` prints the session's
diagnostics and returns true on failure.

## Background

Services are what let one application work with different boards — and different board
revisions — without recompiling:

- Services are **versioned**: the version is part of the type name, for example
  `HololinkInterfaceV1`. Once an interface is published it never changes; new
  capabilities ship as the next version (for example `HololinkInterfaceV2`, usually an
  extension of `V1`). Modules keep publishing older versions too, so already-deployed
  applications keep working.
- Each board's services are implemented in a **device-specific shared library**.
- Device enumeration (bootp) provides a device **UUID**. That UUID and a "compat-id"
  locate the shared object that implements the services for that board.
- The shared object supplies the requested interface by binding its virtual methods at
  runtime.
- Requesting an interface a board does not implement raises an exception — unless you
  pass `allow_null=true`, which tells the framework your application handles the
  missing-service case itself.
